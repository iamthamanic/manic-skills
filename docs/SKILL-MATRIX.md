# Skill Matrix

Kompakte Referenz aller Skills im Repo, gruppiert nach Systembasis. Vollständige Beschreibungen in den jeweiligen `skills/<name>/SKILL.md`.

**How to use** beschreibt eine konkrete Situation, was der Skill dann macht, und ein Beispiel. **Kompatibilität**: ✅ voll · ⚠️ mit Einschränkung — siehe [`TOOL-COMPATIBILITY.md`](TOOL-COMPATIBILITY.md).

Legende für Tool-Spalten: **C** = Cursor · **W** = Windsurf · **P** = pi.dev · **CC** = Claude Code

## Ponytail (YAGNI/Minimalismus)

| Skill | Trigger | Zweck | How to use | C | W | P | CC |
|-------|---------|-------|------------|---|---|---|----|
| `@ponytail` | `ponytail`, `be lazy`, `yagni`, `do less`, `shortest path` | Lazy-senior-dev-Modus, YAGNI-Ladder | **Situation:** Du willst eine Funktion bauen und neigst zu Over-Engineering. **Was passiert:** Aktiviert persistenten Modus: YAGNI-Ladder — fragt zuerst "Braucht es das überhaupt?", dann stdlib, dann native platform, dann already-installed dep, dann one-liner, dann minimum code. Intensitätslevel: `lite`/`full`/`ultra`. **Beispiel:** `@ponytail` → User: "Baue einen Cache für API-Responses" → Skill: "Meinst du `@lru_cache(maxsize=1000)`? Custom Cache-Klasse wäre Over-Engineering." → User nimmt one-liner → `// ponytail: lru_cache, custom class wenn lru_cache messbar knapp`. | ✅ | ✅ | ✅ | ✅ |
| `@ponytail-review` | `review for over-engineering`, `what can we delete`, `/ponytail-review` | Review nur auf Over-Engineering | **Situation:** Code-Review ist fertig, du willst zusätzlich auf Over-Engineering prüfen. **Was passiert:** Findet: reinvented stdlib, unneeded deps, speculative abstractions, dead flexibility. Eine Zeile pro Finding: Location, was cutten, was es ersetzt. **Beispiel:** `@ponytail-review` → "src/utils/cache.ts: Custom Cache-Klasse mit 80 Zeilen, `@lru_cache` deckt das in 1 Zeile" → Finding: cut custom class, use stdlib. | ✅ | ✅ | ✅ | ✅ |
| `@ponytail-audit` | `audit this codebase`, `find bloat`, `/ponytail-audit` | Whole-Repo-Audit auf Over-Engineering | **Situation:** Du erbst ein Codebase und willst wissen, was überflüssig ist. **Was passiert:** Scannt das gesamte Repo (nicht nur Diff), gibt ranked Liste: was löschen, vereinfachen, durch stdlib/native ersetzen. One-shot report, wendet keine Fixes an. **Beispiel:** `@ponytail-audit` → "1. src/utils/cache.ts: Custom Cache → lru_cache (-79 Zeilen) / 2. src/components/Modal.tsx: Custom Modal → Radix Dialog (-120 Zeilen) / 3. ..." → Report, du entscheidest was zu fixen ist. | ✅ | ✅ | ✅ | ✅ |
| `@ponytail-debt` | `ponytail debt`, `what did ponytail defer`, `ponytail ledger` | `ponytail:`-Kommentare → Debt-Ledger | **Situation:** Ponytail hat `// ponytail:`-Kommentare im Code hinterlassen, du willst sie tracken. **Was passiert:** Erntet alle `ponytail:`-Kommentare in ein Debt-Ledger, damit die bewussten Shortcuts nicht vergessen werden. One-shot report. **Beispiel:** `@ponytail-debt` → "3 shortcuts gefunden: (1) `// ponytail: global lock, per-account locks wenn throughput matters` (2) `// ponytail: naive heuristic, O(n²) bei >10k items` (3) ..." → Ledger-Report. | ✅ | ✅ | ✅ | ✅ |
| `@ponytail-gain` | `ponytail gain`, `what does ponytail save`, `/ponytail-gain` | Ponytail-Impact-Scoreboard | **Situation:** Du willst sehen, was Ponytail an Code/Kosten/Zeit spart. **Was passiert:** Kompaktes Scoreboard: less code, less cost, more speed, aus Benchmark-Medianen. One-shot display, keine persistent mode. **Beispiel:** `@ponytail-gain` → "Code: -2,400 Zeilen / Dependencies: -4 / Build time: -18s / Bundle size: -120 KB" → Scoreboard. | ✅ | ✅ | ✅ | ✅ |
| `@ponytail-help` | `ponytail help`, `how do I use ponytail`, `/ponytail-help` | Quick-Reference-Card für Ponytail-Modi | **Situation:** Du willst alle Ponytail-Kommandos sehen. **Was passiert:** One-shot Display aller Modi, Skills, Kommandos. **Beispiel:** `@ponytail-help` → Card: `@ponytail lite|full|ultra` / `@ponytail-review` / `@ponytail-audit` / `@ponytail-debt` / `@ponytail-gain` / `stop ponytail`. | ✅ | ✅ | ✅ | ✅ |
