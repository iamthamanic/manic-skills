# Verify UI

Runtime UI/UX verification after implementation. Answers: **Does it work in the browser? Does it match the intended UX?**

This skill is **project-agnostic**. Never hardcode stack, ports, or product names. Discover everything from the repo.

## Pipeline position

```
@pingpong-solution  →  @implement  →  @verify-ticket  →  @verify-ui  →  @review-ticket
```

**Prerequisite:** `@verify-ticket` PASS (or user explicitly skips with reason).

Do **not** duplicate static code review (`@review-ticket`). Focus on browser behavior, screenshots, and acceptance criteria.

## Global helper skills (ECC, `~/.cursor/skills/`)

| Helper | Trigger in verify-ui |
|--------|----------------------|
| `@web-design-guidelines` | Prefer **before** browser runs when UI files changed — static a11y/UX checklist (also run by `@ecc-check` Phase E / `@audit-changes`) |
| `@debug` | Step 6/8 FAIL or flaky — root cause (console, network, Playwright trace) before another `@implement` |
| `@security-review` | Auth flows, forms, user-generated content in UI — after Step 6 if relevant |
| `@verification-loop` | Only if Step 4 checks failed — fix via `@implement`, do not claim UI PASS |

**Prerequisite order when UI in scope:** `@web-design-guidelines` (static) → this skill (browser). Do not invent aesthetics here (`@frontend-design` is create-time).

## Workflow checklist

Copy and track progress:

```
Verify UI Progress:
- [ ] Step 1: Resolve app root and stack
- [ ] Step 2: Load project context
- [ ] Step 3: Load acceptance from `.qa/acceptance/` (implement artifact)
- [ ] Step 4: Run technical checks (build/tests)
- [ ] Step 5: Ensure Playwright (detect or bootstrap)
- [ ] Step 6: Run e2e scenarios + capture screenshots
- [ ] Step 7: Apply edge-case matrix (relevant subset)
- [ ] Step 8: Write report (PASS / FAIL / PARTIAL)
```

## Step 1: Resolve app root and stack

Read [references/project-discovery.md](references/project-discovery.md) and determine:

1. **Workspace root** — directory with `.git` or where the user is working
2. **App root** — directory containing the frontend `package.json` with `dev`/`start`
3. **Stack** — Vite, Next.js, CRA, static, or none (API-only)

**Monorepo rule:** If root `package.json` uses `--prefix`, read `.qa/project.yaml` `appRoot` first; otherwise detect the subfolder with `vite.config.*`, `next.config.*`, or `src/main.tsx`.

**No frontend detected:** Stop with report section "Kein Frontend — nur Unit/API-Tests empfohlen". Do not install Playwright.

---

## Step 2: Load project context

Read [references/context-sources.md](references/context-sources.md). Load in order (combine all found):

| Priority | Source |
|----------|--------|
| 1 | `.qa/project.yaml` |
| 2 | `.qa/design/*.md` (from pingpong-solution — context for intent) |
| 3 | `.qa/acceptance/*.md` for the current feature |
| 3 | `.qa/edge-cases.md` |
| 4 | `AGENTS.md` |
| 5 | Styleguide (`docs/UI_STYLEGUIDE.md`, `STYLEGUIDE.md`, `.cursor/rules/*.mdc`) |
| 6 | `README.md`, `package.json` scripts |
| 7 | Git diff + recent user messages (what was just implemented) |

Extract: dev URL, checks command, UI language, design tokens, required states (loading/empty/error/disabled).

---

## Step 3: Load acceptance criteria (from /implement)

Acceptance is **auto-generated by `/implement`** at `.qa/acceptance/<feature-slug>.md`. Do not re-derive intent if that file exists.

### Resolution order

1. **Git diff** — any `.qa/acceptance/*.md` added/modified in current changes (exclude `_template.md`)
2. **Newest file** — latest mtime in `.qa/acceptance/` (exclude `_template.md`)
3. **Branch match** — slug matches git branch name
4. **Fallback only** — infer from git diff + conversation (document "no acceptance artifact" in report)

When found → use **verbatim** as the test plan. Map each Happy Path / Edge Case checkbox to a Playwright step + screenshot.

If checkboxes are unchecked, verify each and note OK/FAIL in report. Optionally update the markdown checkboxes to `[x]` only for verified items in the same session (user may commit).

See [references/acceptance-resolution.md](references/acceptance-resolution.md).

### Fallback (no acceptance file)

Only when `/implement` skipped artifact or file missing:

- **Happy path** — primary user flow from diff
- **Regression** — adjacent screens (nav, modals)
- **Edge cases** — [references/edge-case-matrix.md](references/edge-case-matrix.md)

List assumptions explicitly in report.

---

## Step 4: Run technical checks

From app root or workspace root (per `.qa/project.yaml` or `AGENTS.md`):

```bash
# Prefer project-defined command
npm run checks
# Fallback chain
npm run build && npm test
```

Record exact command and exit code. **Do not claim PASS if checks failed.**

Unit tests (Vitest/Jest) validate logic; this step does not replace browser verification.

---

## Step 5: Playwright — detect, never duplicate

Read [references/playwright-bootstrap.md](references/playwright-bootstrap.md).

### Detection (any match = already set up)

- `playwright.config.ts` / `.js` / `.mjs` in app root or repo root
- `@playwright/test` in `devDependencies`
- Script `test:e2e` or `e2e` in `package.json`
- Existing `e2e/**/*.spec.ts`

**If detected:** Read config (`baseURL`, `webServer`, `testDir`). Use existing setup. Do **not** re-run `npm init playwright`.

**If not detected:** Bootstrap once in **app root**:

```bash
cd <appRoot>
npm init playwright@latest -- --yes --lang=ts --install-deps
```

Then apply stack-specific config from [templates/](templates/) (Vite / Next / generic).

After bootstrap:

1. Add `test:e2e` script if missing: `"test:e2e": "playwright test"`
2. Create `e2e/smoke.app-loads.spec.ts` from template
3. Set `outputDir` to `.qa/test-results` and evidence screenshots to `.qa/evidence/`
4. List all new files in report — ask user before committing bootstrap artifacts

**Conflict rule:** If `AGENTS.md` forbids e2e or Playwright, stop and report the conflict. Do not bootstrap.

---

## Step 6: Run e2e scenarios

### Permanent specs

Run existing `e2e/**/*.spec.ts` first (regression).

### Feature-specific specs

For the current change, create **one** spec at:

```
.qa/runs/<YYYY-MM-DD>-<feature-slug>.spec.ts
```

Use `data-testid`, role, or text selectors from the codebase. Prefer stable selectors; add `data-testid` only if blocking and user agrees.

### Screenshots (required)

Every acceptance step → screenshot:

```
.qa/evidence/<feature-slug>/<NN>-<step-name>.png
```

In Playwright:

```ts
await page.screenshot({ path: '.qa/evidence/<feature>/<NN>-<step>.png', fullPage: true });
```

Also capture on failure via config `screenshot: 'only-on-failure'`.

### Browser MCP (optional supplement)

Use `cursor-ide-browser` only when:

- Playwright cannot express the check yet
- Exploratory UX review ("feels wrong")

Playwright results are authoritative for PASS/FAIL.

---

## Step 7: Edge-case matrix

Apply the **relevant subset** from [references/edge-case-matrix.md](references/edge-case-matrix.md).

Skip cases that do not apply (e.g. no auth in project). Document skipped cases.

Project overrides: `.qa/edge-cases.md` extends or replaces defaults.

---

## Step 8: Report

Use the template in [references/report-template.md](references/report-template.md).

Verdict:

- **PASS** — all critical scenarios OK, checks green
- **PARTIAL** — works but UX/style issues or non-critical gaps
- **FAIL** — broken flow, check failures, or critical AC missed

On FAIL/PARTIAL: give concrete fix list (file hints, selector, expected vs actual). Do not re-run `/implement` automatically unless user asks.

---

## Guardrails

- Never log secrets from `.env`
- `reuseExistingServer: !process.env.CI` in Playwright webServer
- Do not install Playwright in API-only repos
- Respect `prefers-reduced-motion` when testing animations
- UI copy checks use language from styleguide/AGENTS (e.g. Deutsch for Letz Fetz)
- Bootstrap is one-time per project — detect before install
